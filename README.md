# 범죄 통계 및 지역 인프라 기반 도보 경로 탐색 서비스

범죄 통계와 CCTV·가로등 등 지역 안전 인프라 데이터를 도보 네트워크에 반영하여, **최단·안전·균형 경로를 비교하고 탐색할 수 있도록 구현한 경로 안내 서비스**입니다.

이 저장소는 원 프로젝트 전체를 복제하거나 독립적으로 배포하기 위한 저장소가 아니라, 프로젝트에서 직접 구현한 **경로 탐색 알고리즘, 안전도 가중치 모델, 백엔드 API 및 기술 전환 과정**을 보여주기 위해 관련 코드를 선별하여 공개한 포트폴리오용 코드 아카이브입니다.

---

## Project Overview

### 목표

일반적인 최단 경로 탐색에서는 이동 거리만을 기준으로 경로를 선택하기 때문에, 실제 보행 환경에서 사용자가 체감하는 안전성을 충분히 고려하기 어렵다는 문제에서 출발했습니다.

이를 해결하기 위해 도로 네트워크에 범죄 통계와 지역 안전 인프라 정보를 반영하고, 사용자의 목적에 따라 서로 다른 기준의 경로를 비교할 수 있도록 설계했습니다.

### 주요 기능

* 도보 네트워크 기반 경로 탐색
* 범죄 위험도 및 지역 안전 인프라를 반영한 경로 비용 계산
* 최단·안전·균형 경로 비교
* 출발지와 도착지를 실제 도로 네트워크에 연결
* 경로 거리, 예상 소요 시간 및 안전 관련 지표 제공
* REST API를 통한 경로 조회

# Development Process

이 프로젝트는 처음부터 현재의 PostGIS + pgRouting 구조로 구현한 것이 아닙니다.

직접 경로 탐색 알고리즘과 안전도 모델을 구현한 초기 버전을 개발한 뒤, 실제 데이터 규모에서 발생한 성능 문제를 분석하고 최종 구조를 변경했습니다.

```text
안전도 모델 설계
        ↓
OSM 보행 네트워크 그래프 구성
        ↓
자체 A* 경로 탐색 구현
        ↓
가중치 및 그래프 캐싱 적용
        ↓
실제 데이터 규모에서 초기 연산 병목 발생
        ↓
서버 메모리 기반 구조의 한계 확인
        ↓
PostGIS + pgRouting 기반 구조로 전환
        ↓
FastAPI 기반 경로 조회 API 구현
```

## 1. 초기 구현

초기에는 OSM에서 추출한 보행 네트워크를 직접 그래프로 구성하고, 범죄 통계와 CCTV·가로등 데이터를 이용하여 각 도로 구간의 안전도 가중치를 계산했습니다.

이후 자체 구현한 A* 알고리즘을 이용하여 경로를 탐색하고, 반복적인 그래프 생성 및 가중치 계산을 줄이기 위해 캐시 계층을 적용했습니다.

### 주요 구현

* OSM 도로 데이터를 그래프 구조로 변환
* 도로 구간별 안전도 가중치 계산
* 안전 비용을 포함한 A* 탐색
* 탐색 결과 비교 및 경로 유형별 비용 계산
* 그래프 및 가중치 캐시 관리

관련 코드는 [`legacy/`](legacy/)에서 확인할 수 있습니다.

---

## 2. 성능 문제와 구조 변경

초기 구현을 실제 데이터 규모에 적용하면서 **서버 시작 시 전체 도로 그래프와 안전도 가중치를 계산하고 메모리에 캐싱하는 과정의 초기 연산 비용이 지나치게 커지는 문제**가 발생했습니다.

단순히 캐시 구조를 추가하는 것만으로는 최초 계산 비용을 해결하기 어려웠고, 서버 메모리에 대규모 그래프와 가중치를 유지하는 구조 역시 실제 서비스 환경에 적합하지 않다고 판단했습니다.

이에 따라 역할을 다음과 같이 분리했습니다.

| 기존 구현           | 최종 구조               |
| --------------- | ------------------- |
| Python에서 그래프 생성 | PostGIS에서 공간 데이터 관리 |
| Python에서 가중치 계산 | 계산된 가중치를 DB에 저장     |
| 자체 A* 탐색        | pgRouting 활용        |
| 서버 메모리에 그래프 캐싱  | DB를 통한 데이터 관리       |
| 애플리케이션 중심 공간 처리 | DB 중심 공간 처리         |

자체 구현한 알고리즘은 최종 서비스에서 단순히 폐기한 것이 아니라, **경로 비용 모델과 탐색 방식을 검증하기 위한 초기 구현으로 활용했습니다.**

이후 실제 데이터 규모와 서비스 운영을 고려하여 데이터와 탐색 연산을 데이터베이스 중심으로 이전했습니다.

# Final Architecture

최종 구조에서는 대규모 공간 데이터를 애플리케이션 메모리에 유지하지 않고 PostgreSQL/PostGIS에 저장하며, pgRouting을 이용하여 데이터베이스에서 경로 탐색을 수행하도록 변경했습니다.

```text
Client
  │
  │ HTTP Request
  ▼
FastAPI
  │
  ├── 출발·도착 좌표 처리
  ├── 경로 유형 선택
  │
  ▼
PostgreSQL + PostGIS
  │
  ├── 공간 데이터 조회
  ├── 도로 네트워크 관리
  │
  ▼
pgRouting
  │
  └── 경로 탐색
  │
  ▼
FastAPI
  │
  ├── Geometry 가공
  ├── 거리 및 시간 계산
  └── 경로별 통계 생성
  │
  ▼
Client
```

최종 API 구현은 [`final/`](final/)에서 확인할 수 있습니다.

# Key Implementation

## 안전도 가중치

도로 구간별 비용에 이동 거리뿐만 아니라 안전 관련 지표를 반영하여 서로 다른 경로 탐색 기준을 구성했습니다.

이를 기반으로 다음 세 가지 경로를 비교할 수 있도록 구현했습니다.

* **Shortest** — 이동 거리를 우선하는 경로
* **Safe** — 안전 비용을 최소화하는 경로
* **Balanced** — 거리와 안전성을 절충하는 경로

---

## 자체 A* 경로 탐색

초기 구현에서는 OSM 보행 네트워크를 그래프로 구성하고 A* 알고리즘을 직접 구현했습니다.

이를 통해 단순히 외부 경로 탐색 라이브러리를 사용하는 것이 아니라,

* 그래프 노드 및 간선 구조
* 이동 비용
* 휴리스틱
* 탐색 우선순위
* 경로 복원

등 경로 탐색의 핵심 구조를 직접 설계하고 검증했습니다.

관련 구현은 [`legacy/pathfinder.py`](legacy/pathfinder.py)에서 확인할 수 있습니다.

---

## PostGIS + pgRouting 기반 경로 API

최종 구현에서는 PostGIS의 공간 질의 기능과 pgRouting의 네트워크 분석 기능을 활용했습니다.

`main.py`에서는 FastAPI 요청을 받아 출발지와 도착지를 도로 네트워크에 연결하고, `pgr_withPoints`를 이용하여 경로를 계산합니다.

또한 계산된 경로를 지도 UI에서 사용할 수 있도록 Geometry를 가공하여 좌표와 구간별 정보를 반환합니다.

주요 구현 내용:

* 공간 인덱스를 활용한 탐색 대상 제한
* 도로 선분 위 임의 지점의 edge fraction 처리
* 경로 방향에 따른 Geometry 절단 및 반전
* GeoJSON 형태의 경로 데이터 생성
* 경로별 거리 및 예상 시간 계산
* 안전 비용 및 상대 개선율 산출

# API Interface

최종 API에서는 다음과 같은 엔드포인트를 제공합니다.

| Method | Endpoint  | Description      |
| ------ | --------- | ---------------- |
| `POST` | `/route`  | 지정한 기준의 경로를 탐색   |
| `POST` | `/routes` | 최단·안전·균형 경로를 비교  |
| `GET`  | `/health` | 서버 및 DB 연결 상태 확인 |

예시 요청:

```json
{
  "start_lat": 35.856,
  "start_lng": 128.532,
  "end_lat": 35.862,
  "end_lng": 128.548,
  "route_type": "all"
}
```

# 실행 환경

본 저장소는 원 프로젝트 전체 실행 환경을 포함하지 않으며, 공개된 코드의 구조와 구현 방식을 확인하기 위한 코드 아카이브입니다.

`final/main.py`의 실행 환경에는 다음이 필요합니다.

* Python
* FastAPI
* SQLAlchemy
* psycopg2
* PostgreSQL
* PostGIS
* pgRouting

DB 연결 정보는 환경 변수 `DATABASE_URL`을 통해 구성합니다.

실제 서비스 데이터와 DB 접속 정보는 저장소에 포함하지 않습니다.
